# Evidencia — HU-R7-03: Proteger rutas y datos por rol y gerencia

**Fecha:** 11/10/2026 · **Entorno:** macOS, Node 22.16.0, PostgreSQL 14.20 (local)

La autorización vive en el backend (RN_1, CA_4). Cada ruta con datos declara qué roles la usan
y recibe la sesión ya verificada contra la base. La gerencia sale de la sesión, nunca de la
petición (RN_2). El frontend tiene una guardia de páginas, pero es una comodidad: oculta una
pantalla que de todos modos no podría pedir sus datos.

## Qué se entrega

| Pieza | Ruta |
|---|---|
| Middleware: 401 sin sesión, 403 por rol | `src/autorizacion.ts` — `crearProtegida(roles, manejador)` |
| ¿Puede esta sesión abrir esta página? | `GET /api/auth/acceso?pagina=…` (usa la tabla de `src/rutas.ts`, lista blanca) |
| Consulta de indicadores filtrada por gerencia | `src/indicadores.ts`, `src/datos/indicadores.ts` — `GET /api/indicadores`, `POST /api/indicadores/buscar`, `GET /api/indicadores/:id` |
| Configuración, solo Administrador | `GET /api/admin/configuracion` |
| Rutas con parámetro | `src/http.ts` — `/api/indicadores/:id` |
| La sesión trae `gerenciaId` de `usuarios` | `src/datos/sesiones.ts` |
| Guardia de páginas en el navegador | `session.js` — `protegerPagina()`, corre sola en las 28 páginas protegidas |
| 403 real al pedir la página | `src/sitio.ts` consulta `/api/auth/acceso` antes de servir cada página protegida |
| Pruebas | `pruebas/autorizacion.test.ts` (26) · `pruebas/guardia-frontend.test.ts` (5 de R7-03) |

## Criterios

| CA | Estado | Evidencia |
|---|---|---|
| **CA_1** Enlace en /dashboard-revisor o /dashboard-admin → 403 y a su dashboard | Cumplido | §2: el servidor responde 403 con redirección a `dashboard-enlace.html`; la guardia del navegador hace lo mismo sin mostrar la página |
| **CA_2** sin sesión, cualquier ruta protegida → /login | Cumplido | §2: página → 302 a `/login.html`; API → 401. La guardia guarda la página para volver tras el login |
| **CA_3** `/api/admin/*` → 403 a Enlace y Revisor con token válido | Cumplido | §2 y prueba por cada ruta de `/api/admin/` |
| **CA_4** la verificación de rol ocurre en el backend | Cumplido | Toda la verificación de §1 y §2 es del backend; el frontend no participa |
| **CA_5** un Revisor no ve indicadores de otra gerencia manipulando URL o cuerpo | Cumplido | §2: `?gerencia_id` y `gerencia_id` en el cuerpo se ignoran; un id de otra gerencia es 404, igual que uno que no existe |
| **CA_6** `/admin/configuracion` solo del Administrador | Cumplido | §2: `configuracion.html` y `/api/admin/configuracion` dan 403 a Revisor y Enlace |
| **RN_1** middleware en backend; guards del frontend no son la seguridad | Cumplido | `crearProtegida`; la guardia de `session.js` se muestra si el backend falla, porque los datos igual los niega él |
| **RN_2** la gerencia de la sesión no se sobrescribe | Cumplido | Con sesión en servidor (no JWT), la gerencia se lee de `usuarios` en cada petición: un cambio de gerencia aplica en la siguiente (prueba) |
| **RN_3** un solo rol por usuario | Cumplido | `usuarios.rol` es una columna; un cambio de rol aplica en la siguiente petición (prueba) |

Nota de la HU: el Administrador conserva el acceso global, y la unidad del Enlace es informativa
(ve toda su gerencia). Ambas cosas están probadas.

## Decisiones

- **Otra gerencia es 404, no 403.** Un 403 confirmaría que el indicador existe. La pregunta 3 de la
  propuesta de sesión la dejaba abierta; se tomó la recomendación.
- **Lista blanca de páginas.** Una página que no está en `src/rutas.ts` se niega a todos. Una página
  nueva hay que agregarla a propósito.
- **`/api/frecuencias` sigue pública.** Es el catálogo de TEC-03 y no tiene datos sensibles; su
  configuración editable vive en `/api/admin/configuracion`.
- **Producción.** El 403 de página lo da quien sirve el HTML. `src/sitio.ts` muestra cómo:
  consultar `GET /api/auth/acceso` antes de servir (en nginx, `auth_request`). Si el hosting no
  puede hacerlo, queda la guardia del navegador y la API, que es la que protege los datos.

## Límites

- Lo verificado en navegador simulado (guardia, redirecciones) no sustituye verlo en un navegador
  real; las respuestas HTTP de §2 sí son reales.
- Una ruta inexistente bajo `/api/admin/` responde 404 a cualquier rol: no hay nada que proteger.
